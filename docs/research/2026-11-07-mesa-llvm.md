# Mesa and LLVM in the image: never loaded by Chromium

**Date:** 2026-11-07 · **Read against:** branch `build/prod-without-npm` (`feb39bc`, the prod image
without npm), Alpine 3.24.4, `chromium-headless-shell` 156.0.8078.79-r0, `mesa` 26.1.6-r0,
`llvm22-libs` 22.1.3-r1 · **Decision taken from it:** `deploy/Dockerfile` deletes `libLLVM` and
`libgallium` in the layer that installs them.

## Question

The prod image was ~1.2 GB, and `/usr/lib/libLLVM.so.22.1` alone was 167.8 MiB. Does Chromium
need it, given that the service launches it with `--disable-gpu` (and
`--disable-software-rasterizer`) and that Chromium ships its own SwiftShader, `libEGL.so` and
`libGLESv2.so` in `/usr/lib/chromium`?

## Where it comes from

- `chromium-headless-shell` depends on `mesa-dri-gallium` and `so:libgbm.so.1` (`mesa-gbm`).
- Both depend on the `mesa` package, whose `/usr/lib/libgallium-26.1.6.so` (35.5 MiB) holds
  Mesa's Gallium drivers. It links `libLLVM.so.22.1` (`llvm22-libs`, required by nothing else)
  and `libSPIRV-Tools.so` (`spirv-tools`, 5.3 MiB).
- `/usr/lib/dri/*_dri.so` are links to `libdril_dri.so` (132 KiB), which loads `libgallium`;
  `/usr/lib/gbm/dri_gbm.so` (`libgbm`'s backend) links it too, and so do Mesa's
  `libEGL.so.1`/`libGLESv2.so.2`.
- The shell binary's own `DT_NEEDED` (`scanelf -n`) includes `libgbm.so.1` and `libdrm.so.2`, but
  no Mesa EGL/GLES, no `libgallium` and no LLVM. `libgbm.so.1.0.0` itself needs only `libdrm`,
  `libexpat` and musl; it would only load a backend (`dri_gbm.so` → `libgallium` → LLVM) with
  `dlopen` when asked to open a GPU device.

## Method

1. **Mapped libraries.** A sampler inside the container read `/proc/<pid>/maps` of every Chromium
   process every 50 ms while the service rendered the reference requests (`simple`, `rich`, `long`,
   `screenshot`) and `/selfcheck`. Both modes: sandbox off (browser, GPU process, renderers) and
   `CHROME_SANDBOX=1` with the Kubernetes profile, `--cap-drop ALL` (plus zygotes and broker).
2. **Attempted opens.** `strace -f -e trace=openat,open,access,stat` of the whole service (node and
   every Chromium process) for `simple`, `rich`, `screenshot` and `/selfcheck`.
3. **Removal.** `rm -f /usr/lib/libLLVM*.so* /usr/lib/llvm*/lib/libLLVM*.so* /usr/lib/libgallium-*.so`
   in the same `RUN` as `apk add`; then the whole suite, the maps and the trace again, and
   `scripts/benchmark.mjs` two rounds per image, old vs new, on arm64, plus the reference outputs
   on amd64 (Rosetta).

## Results

**Before the removal**, in both sandbox modes, the union of mapped libraries of all Chromium processes
(127 distinct `.so`) contains from the graphics stack only `libgbm.so.1.0.0`, `libdrm.so.2`,
`libxcb-dri3.so.0` and `libva-drm.so.2`. Not mapped: `libLLVM`, `libgallium`, any `dri/*_dri.so`,
`dri_gbm.so`, Mesa's `libEGL`/`libGLESv2`, and also Chromium's own `libEGL.so`, `libGLESv2.so`,
`libvk_swiftshader.so` and `libvulkan.so.1`. The trace has no `open`/`stat` of any of them, not even
failing ones: the only graphics library opened is `libgbm.so.1`, once per Chromium process (7).

**After the removal**: the same 127 libraries are mapped in both modes and the trace is the same.

| --- | --- | --- |

| files in the prod image, amd64 | 865,820 KiB | 636,392 KiB (**−224 MiB**, −27%) |
| apk layer, arm64 / amd64 (`docker history`) | 699 MB / 735 MB | 486 MB / 501 MB |
| `yarn test`, all three modes (CI's commands) | 96 passed | 96 passed |
| `/selfcheck`, both platforms | 200 | 200 |

`scripts/benchmark.mjs`, arm64, anonymous peak MiB (round 1 / round 2):

| scenario | before | after |
| --- | --- | --- |
| idle | 34 / 34 | 34 / 34 |
| selfcheck | 85 / 80 | 84 / 82 |

No failed requests and no leftover Chromium processes in any run; latencies the same within noise.
`scripts/compare-references.mjs`: same page count, page size and 0.0% differing pixels for
`long.pdf` (60 pages), `rich.pdf` and `simple.pdf`, same dimensions for `screenshot.png`, on arm64 and
amd64. The arm64 PNG is byte-identical, the PDFs differ only in their creation dates.

`apk` keeps working: `apk add` of another package succeeds afterwards. `apk audit --system` lists
the five deleted files as missing, as expected.

## Verdict

With `--disable-gpu`, Chromium never loads Mesa's Gallium drivers or LLVM, in either sandbox mode,
so `deploy/Dockerfile` deletes `libLLVM` and `libgallium` right after `apk add`. `libgbm` stays: the
binary links it.

What would bring them back into play, and then needs this checked again:
- enabling the GPU or WebGL (dropping `--disable-gpu`, `--enable-unsafe-swiftshader`, `--use-gl=…`),
  which can make `libgbm` open a device and `dlopen` `dri_gbm.so`;
- a Chromium or Mesa update that links `libgallium` or LLVM directly (check `scanelf -n` of the
  shell binary);
- a later `apk upgrade` or `apk fix` of `mesa`/`llvm*-libs` in another layer, which would put the
  files back.

Not done: `spirv-tools` (5.3 MiB) and the rest of `mesa-dri-gallium`/`mesa-egl`/`mesa-gles`
(< 1 MiB) stay, since the size gain does not justify more deleted package files. Not verified:
other architectures than amd64 and arm64, and memory on amd64 (only its reference outputs).
